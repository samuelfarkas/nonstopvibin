# Storage and profile boundaries

The desktop app, development runs and the headless server keep their data in `~/.nonstopvibin` on macOS and Linux. **Settings → Open data folder** reveals it. SQLite, `vault.key`, profile credentials and configs, agent connection helpers, and installed core updates (`cores/`) live here. While the daemon runs, `server.json` and `server.lock.sqlite` are here too, in desktop mode as well as on a server (described below). On Linux the window process keeps its web storage and cache in an owner-only `webview/` folder here; on macOS WebKit keeps them in its default location for the app. When the window process cannot start, the browser opens an owner-only `browser.html` here that leads to the session, so the token stays out of the opener's arguments. The daemon logs to standard error and writes no log or crash-dump files. `NONSTOPVIBIN_DATA_DIR` overrides this entire root. `NONSTOPVIBIN_PORT` overrides the desktop app's port, 4318 (`DESKTOP_PORT` in `crates/cli/src/run.rs`); the headless server takes `--port` and defaults to 4320. Use a separate data override when testing alongside the desktop app. An app update starts the new version with the old one's environment, so both overrides survive it. The first update from an Electron build is the exception: Squirrel.Mac relaunches without them, so that launch opens with the defaults.

To reset, quit the app completely (closing its window leaves it running), stop any development server using the same directory, delete the data folder, and reopen. No old location is automatically imported, so deleted accounts cannot reappear from an older installation. Earlier builds used `~/Library/Application Support/nonstopvibin` on macOS, normally `~/.config/nonstopvibin` on Linux, and repository-local `.runtime` in development. Those folders remain untouched.

Back up the data folder with the app fully stopped, keeping the database and its matching `vault.key` together. An existing database without its key is rejected; restore the matching key from backup. Generating a replacement cannot recover its secrets.

OS-managed login items, native agent configuration in other tools/projects, files you explicitly export, and external browser sign-in state are outside this folder. Disable launch at login and disconnect agents before deleting app data to remove those integrations. The agent credential broker also uses a private `/tmp/nonstopvibin-…` Unix socket directory because macOS limits socket path length; it stores no persistent account data. The installed application and OS-managed diagnostics remain managed by the operating system.

API keys and internal keys in SQLite are encrypted with AES-GCM using `vault.key` in the same data directory, in both desktop and development. The database and key are owner-only (0600 in a 0700 directory); software that can read both can decrypt the secrets. No system keychain is required. **The upstream process also needs plaintext credentials:** generated config and OAuth files are owner-only (0600 in 0700 directories), not encrypted while on disk. This is separation between account pools, not an OS security boundary against software running as your user.

The headless server (`nonstopvibin serve`, see [Run on a Linux server](server.md)) is the same daemon without the tray or the window process, with desktop and development modes off. The desktop app follows the same start-up, lock and discovery rules; a second launch finds the running app through `server.json` and asks it to show its window. After it starts, the daemon writes `server.json` (PID, port, session token, allowed hosts, version) atomically as an owner-only file in the data folder; `nonstopvibin url` and `status` read it and confirm an authenticated `/api/state` response, so a stale file or recycled PID is never reported as running. A clean shutdown removes the file only if it still names its own PID. An owner-only `server.lock.sqlite` holds a single-writer SQLite transaction before store/core initialization until shutdown completes; it is never unlinked, and the OS releases its lock on a crash. This rejects concurrent instances even during startup on different ports. Termination signals are handled before initialization and cancel restoration, awaiting spawned core cleanup before releasing ownership. The token rotates with every process; `serve` includes it only when attached to a terminal, never in journald, while `url` prints it intentionally for session discovery. A missing core is fatal at startup, and on a server the core's hash must match both its manifest and the pin compiled into the daemon (desktop signing rewrites the core, so the desktop app checks it against its refreshed manifest); an installed core update must match its manifest, and matched a reviewed pin when it was installed. `--allow-host` adds one exact HTTPS host name (for example Tailscale Serve) for the web UI and management; the agent gateway and WebSockets still answer only on loopback.

The gateway binds only to 127.0.0.1. Agent keys cannot access management. Host/Origin checks protect local management requests. Provider sign-in uses the external browser and a state-validated loopback callback. The window process accepts bridge calls only from the main frame of a page on the daemon's origin, parses each against a fixed list of nine methods, and denies navigation to other origins, new windows, and downloads. The page has no other native access.

Native agent connection files contain no profile credentials. Claude Code, Codex,
and pi obtain keys through their native credential command support. They use an
owner-only local Unix socket.
The socket has no management operations and is not reachable over TCP. Native
configuration fixes the profile URL; app startup updates owned connections after a port
change; until then the credential helper refuses to return a key for a different port. Existing settings
are preserved; conflicting edits are refused. Disconnect removes owned settings,
but does not revoke cached credentials: restart the agent, or quit the app to
stop access. Software running as your OS user remains inside the trust boundary.
Legacy launcher files from earlier builds can still use the private broker; native
setup replaces the onboarding flow without deleting those existing files.

Request bodies, API keys, generated responses, and raw upstream error bodies are not written to the activity database. Accounting is drained shortly after a gateway request ends, and once more a little later for events the core publishes late; a slower fallback applies only while a request or WebSocket stays open. With no gateway traffic, collection sleeps until the next request. Full queue pages keep fast polling active; a failed drain is retried at once, then with a growing, capped delay. Stopping rejects new proxy requests and drains every queued accounting page before terminating the core. In-flight requests can be interrupted, and events not yet published by the core may be unavailable. The database survives restarts, but a crash between upstream completion, queue collection, and SQLite commit can lose accounting events; this is not a billing ledger. Activity shows/exports the most recent records for its selected period, up to `usagePageSize` in `src/shared/vocabulary.ts`; request totals, normalized token totals, and estimated API value cover the entire selected period. The all-time range includes all retained history. Provider quota reads repeat while the interface is open, and may be delayed by slow providers. Older readings are visibly stale; when the interface opens again, stale readings refresh in the background. The refresh period, the interface's poll and the staleness limit are `quotaRefreshMs`, `pollMs` and `quotaStaleMs` in `src/shared/vocabulary.ts`; the daemon's own periods are `TIMING` in `crates/accounts/src/scheduler.rs`.

Account and quota maintenance runs separately from accounting collection, so a slow provider does not delay draining usage. Account status refreshes periodically while the interface is open, and its first read after a pause waits briefly for current status. The CLI's state reads poll nothing. Unchanged account metadata does not rewrite SQLite, credential file permissions are corrected only when they differ from owner-only, and Claude account identities are re-read only when their credential file changes. Optional activity retention deletes older records on apply, startup, and daily; aggregate totals then cover retained history. SQLite reuses freed pages without an automatic blocking vacuum.

The store keeps no cached usage summaries. Activity period summaries and prices share the aggregate described below, so ingestion and retention do not maintain a separate summary cache.

Each running profile has its own core process. Stopping it, or quitting the app, sends SIGTERM and then SIGKILL after a grace period (`KILL_GRACE` in `crates/core/src/processes.rs`); a new core that does not answer in time (`READY` in `crates/core/src/pool.rs`) is stopped the same way. A profile without an OAuth subscription starts its core on its first gateway request, model catalog read or interface open, and stops it after an idle period (`TIMING.idle`) without requests, an open interface, a pending sign-in, or a cooldown the core still holds for one of its keys; its usage is drained first, and a request that arrives meanwhile waits for the next core. A profile with an OAuth subscription keeps its core running so the core can refresh its tokens. A profile the app keeps running is restarted, including one whose very first start failed: when its core exits or fails to start, the scheduler starts it again, shortly after an exit, and checks its quota. Each such start runs on its own, so it delays neither another profile's start nor account and quota maintenance; shutdown abandons a start still waiting for its core. A core that keeps failing is retried after delays that double up to a cap, and its failure enters the error list once (a failure the launch already reported counts). After a fixed number of failed starts in a row, the app stops restarting the profile: the profile shows that it stopped and the error list says so once. A failed start counts, and so does a core that exits before it has stayed up for the longest delay since its start ended; once a core has stayed up that long, the count starts over. The first delay, the cap and the number of starts are `RESTART_TIMING` in `crates/accounts/src/restart.rs`. Restart, **Refresh** or a subscription change that starts the profile and leaves its core running also starts the count over and brings back a profile the app stopped restarting; if that start fails, nothing changes: the count and the next retry stay, and a profile the app stopped restarting stays stopped. Relaunching the app starts over too: a profile it cannot start is retried with a fresh count. While a start, stop or subscription reconnect of the profile is under way, the retry waits for it to end instead of waking the scheduler. **Refresh** starts such a profile before checking quota; quota of API-key subscriptions is checked even when the start fails. Each core is also paired with a `/bin/sh` watchdog that waits on a pipe from the app without waking up. If the app ends without stopping the core, including a crash or force quit, the pipe closes and the watchdog stops the core after confirming its start time and command line. Running cores are also recorded in `core-processes/` in the data folder (pending sign-in stores under `oauth-pending/` keep their own record). At startup, before starting any core, the app stops each recorded core whose owning instance has exited and whose start time and command line still match a core of this data folder, then removes stale records. Both safeguards rely on `ps`; without it only normal shutdown stops cores.

Installed builds (the packaged desktop app and the packaged server) keep core updates in `cores/<version>/` in the data folder, each executable beside its manifest. A download stays in `cores/.staging-*` until it matches the reviewed pin's hashes and starts on a throwaway store under `oauth-pending/`. At startup, before any core runs, the app selects the newest entry above its bundled core whose manifest names that version and this platform and architecture and whose executable still matches the manifest's hash, and deletes every other entry. Without one it verifies the bundled core as before. Installing or reverting waits for sign-in actions and subscription changes, refuses while a sign-in is pending, then stops and starts each running profile on the new core; a profile that does not start again is reported. Development runs never select or delete installed cores. See [Updating the CLIProxyAPI core](releases.md#updating-the-cliproxyapi-core).

The background scheduler sleeps until the next accounting, maintenance, idle-stop, or cleanup deadline. Starting a profile or receiving gateway activity brings accounting forward; with no running profiles and no profile due a restart (one the app stopped restarting is not due), only daily history cleanup remains scheduled. Display refresh timers stop while the interface is hidden and refresh immediately when shown. Sign-in polling continues while users complete authentication in their browser.

The daemon starts the window process when the main window or quota popup opens, and the process exits when its last window closes, which ends every WebKit process with it. Unfinished main-window forms prevent unloading, and the window hides instead. The proxy and the tray remain available without a window process. The tray changes only when the daemon's status or activity changes, and the interface's logo settles to static artwork after a finite opening or click animation. Core configuration enables upstream `commercial-mode` to skip request/response body logging middleware; this upstream option does not change the app's MIT license. Usage accounting remains enabled. Binary integrity verification streams the pinned core instead of reading it into one buffer.

A hidden window retries its deferred close when a draft or operation guard clears. Remaining forms and operation errors still prevent unloading, and reopening cancels the deferred close. The webview caches Vite's fingerprinted UI assets for a year; HTML and unhashed assets revalidate with an ETag that changes with every launch of the daemon. Management responses remain `no-store`.

When migrating a refresh-token account, avoid running both apps against that same account during sign-in or token refresh. A provider may rotate the token, leaving the other copy outdated. Claude sign-in asks you to confirm the organization and destination profile before making the subscription available. Seats are distinguished by the provider's account and organization UUIDs, so the same email can connect to multiple organizations. Choose **Connect another organization** after connecting the first seat. Reconnecting the same seat preserves its connection ID, history, label, priority, and paused state; a running destination profile briefly restarts to safely replace its credential. A stopped profile is not started by the reconnect; the app then starts it again like any profile with subscriptions, unless it has stopped restarting that profile.

Duplicate detection is local to each profile: matching Claude seats, access/refresh tokens, and API credentials are rejected within that profile. The same subscription can be assigned to multiple profiles; requests then consume the same upstream subscription and independently stored OAuth credentials can become outdated after token rotation. Assign subscriptions deliberately when work and personal quota must stay separate. Older Claude files lacking those UUIDs display **Organization unverified** and are never merged by email; they must be connected separately and the obsolete entry removed. Other providers and unidentified legacy credentials can still represent the same upstream account, so assign those deliberately.

Full-period API values use the same validated provider-specific accounting and context-price tiers as individual records. Unknown prices or incomplete token breakdowns are reported as missing, never free. The daemon retains one aggregate per profile, reads at most 500 history rows per SQLite call, and yields to its runtime between pages. Unchanged refreshes read no history rows; new records add to the total and an advancing cutoff subtracts only newly expired records. Widening the period, retention, or a new model-price catalog rebuilds the aggregate. Calculations freeze the catalog for consistency and retain totals rather than history rows. Raw provider counters remain available in CSV; the displayed token mix uses non-overlapping counters and labels unclassified tokens explicitly.
